# Трекер аудита безопасности API

## Назначение

Поддерживать единый источник правды по прогрессу hardening-а API в проекте:

- замечания аудита по **URL + HTTP-методу**;
- статус исправлений;
- добавленные unit/integration тесты;
- оставшиеся риски и follow-up задачи.

Основной файл трекинга:

- `/home/yurgen/PycharmProjects/tetris/docs/api_security_audit_tracker.md`

## Когда вызывать

Использовать этот скилл, когда:

1. Пользователь просит продолжить аудит безопасности backend endpoint-ов.
2. Пользователь просит обновить трекер после внедрения фикса.
3. Нужно зафиксировать, какие unit-тесты были добавлены.
4. Нужен прогресс-отчет: что уже исправлено и что осталось.

## Обязательные правила реализации

1. **Права и доступ**
   - У каждого endpoint должен быть явный `permission_classes`.
   - Если используется `TerminalActionBasedPermission`, должны быть заданы `required_actions`.
   - Если endpoint не предназначен для клиентов, явно указывать `worker_only = True`.
   - Для чувствительных API недопустимы `AllowAny` и `permission_classes = []` без отдельного согласованного обоснования.

2. **Фильтрация по доступным терминалам**
   - Для terminal-зависимых данных обязателен `QuerysetByAccessibleTerminalsMixin`.
   - Обязательно корректно задавать `terminal_field_id_in` для текущей модели/связей.
   - Выборка должна идти через `get_queryset()`; нельзя обходить фильтрацию прямым `self.queryset`.

3. **Защита от IDOR (object id)**
   - Нельзя делать `Model.objects.get(pk=...)` без scoped-фильтрации доступа.
   - `retrieve/update/delete` должны работать только через queryset, ограниченный доступом.
   - В batch-операциях проверять каждый id в пределах доступного scope.

4. **Защита от подстановки чужого terminal id**
   - **`terminal_pk` в URL kwargs**: `TerminalActionBasedPermission` автоматически проверяет доступ через `_get_user_terminal(user, terminal_pk)` → кидает `PermissionDenied`, если терминал недоступен. Дополнительная валидация не нужна.
   - **`terminal_id` в body без `terminal_pk` в URL**: `TerminalActionBasedPermission` перебирает все терминалы пользователя и пропускает если хотя бы один доступен — `terminal` из body **НЕ проверяется**. Здесь нужна явная валидация: проверить, что `terminal_id` из body входит в `UserTerminal.objects.filter(user=request.user, deleted=False).values_list('terminal_id', flat=True)`.
   - Для create/update проверять связку `object -> terminal -> client/user`.

5. **Клиентский доступ (`user_type=2`)**
   - Для клиентских endpoint обязателен корректный `client_field`.
   - Если клиентский доступ не предусмотрен, endpoint должен быть явно worker-only.

6. **Тесты и фиксация результата**
   - На каждый фикс добавлять unit/integration тесты минимум по 3 сценариям:
     - запрет доступа к чужому `object id`;
     - запрет работы с чужим `terminal id`;
     - корректный доступ в рамках своего scope.
   - После фикса обязательно обновлять трекер по строке `URL + метод`.

## Процесс работы

1. Открыть трекер и найти строку нужного app/URL/метода.
2. Если endpoint новый — добавить строку с URL + методом и колонками критериев.
3. Обновить колонки критериев:
   - права и доступ;
   - фильтрация по доступным терминалам;
   - защита от IDOR (подстановка object id);
   - защита от подстановки чужого terminal id;
   - клиентский scope (`client_field`).
4. В релевантной ячейке оставить краткую и предметную пометку:
   - что изменено;
   - где исправлено (файл/функция);
   - какой тест добавлен.
5. Формулировки держать короткими и проверяемыми.

## Нотация статусов (рекомендуется)

- `ОК` — критерий выполнен.
- `Замечание: ...` — проблема остается.
- `ОК (fixed in <file:line>, test: <test_name>)` — исправлено и покрыто тестом.

## Правила качества

- Всегда трекать по **URL + методу**, а не только по View-классу.
- Если один view обслуживает несколько методов, вести отдельные строки на каждый метод.
- Исторический контекст не удалять без необходимости; обновлять статус в существующей строке.
- Если информация неполная, явно помечать это и добавлять follow-up пункт.

## Пример обновления

До:

`| /api/container/<id>/ | PUT | ContainerUpdateView | ОК | Замечание: ... | Замечание: ... | ОК | Замечание: ... |`

После фикса:

`| /api/container/<id>/ | PUT | ContainerUpdateView | ОК | ОК (fixed in container/views.py:123) | ОК (test: test_container_update_scope) | ОК | ОК |`
